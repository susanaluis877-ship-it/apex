# Apex 流程开发

用户只描述想要的流程，你自己完成：准备环境 → 看页面 → 探索 → 在宿主项目里写流程代码 → 编译安装 → 校验 → 真机运行 → 修到通过 → 交付。
交付的是固化下来的流程代码（Java DSL），运行时不需要 AI。只有这些事需要人：手机上的密码或锁屏、登录 / 验证码 / 支付确认、不可逆操作的许可、最终审阅。

## 工具

两种用法，功能相同：

- **MCP 工具**（装了插件时可用，名字里带 `apex`）：`doctor`、`setup`、`deploy`、`observe`、`act`、`suggest`、`find`、`find_text`、`launch`、`plan`、`history`、`features`、`validate`、`check`、`run`、`export`、`push`。`observe` / `act` 默认同时返回页面结构和带编号框的截图。
- **命令行**：`python3 ${CLAUDE_SKILL_DIR}/scripts/apex.py <命令>`，命令名相同（`find_text` 写成 `find-text`），`-h` 看参数。截图加 `--shot annotated`，输出里有 PNG 路径，用 Read 查看。

`validate` / `check` / `run` / `export` 的流程参数写宿主代码里 DSL 流程的引用，例如 `com.foo.flows.ShopFlows#dailyCheckin`（静态、无参、返回 Flow 的方法）；也接受 JSON 文件。

**两种模式，自动切换**：Apex 调试桥能用且无障碍服务已连接时，`observe` / `act` 走 Apex（页面结构和 Apex 运行时看到的一致，选择器在设备上验证）；宿主没装、服务没开时自动改用 **adb 模式**（uiautomator 看页面、input 操作），只用来做安装、开启服务这类准备工作，输出开头会标明。adb 模式下看到的选择器不要写进流程。

页面结构里每个可操作元素是一行：`@引用 类型 "标签" 状态 (中心坐标)`。没有自己文字的容器显示成 `含「A」「B」`，A、B 是它里面各个节点的文字，要分开用，不能把整串当成一个文本。`@引用` 只在当前这一屏有效；`act` 会把它换成在设备上验证过的选择器并告诉你用了哪个——写流程时用那个选择器。

## 绝对不要

- 不要自己调用 `uiautomator dump`、uiauto.dev / uiautomator2、Appium、Maestro、mobile-mcp：它们连接期间会让 Apex 的无障碍服务断开，而且看到的树和 Apex 不一样。需要 adb 模式时 `observe` / `act` / `setup` 会自己判断、自己切换。
- 不要 `am force-stop` 宿主 App（会把无障碍服务从已开启列表里移除，要人重新开）。重置页面用 `launch --reset`。
- 不要点「强行停止」「卸载」「清除数据」「恢复出厂设置」这类按钮；不要改与任务无关的设置。
- 付款、发消息、删除别人的数据、下单、提交表单这类不可逆操作，探索时先问人。遇到登录、验证码，交给人。
- 任务本身就是删除、清理这类不可逆操作时：先自己造一份测试数据（例如新建一个同名的条目），拿它练习和测试；真正执行前用 `expect` 的 `has` / `hasNot` 核对选中的是哪一项、没有误选别的。流程里也要有同样的保护：删除前的状态条件写明「选中的是目标、没有选中其他项」，不满足就以 failure 结束，绝不删除。
- 文字一律从页面结构里复制，不要从截图里认字。

## 第 0 步：环境

1. `doctor`。
2. 宿主没装、或无障碍服务没开：`setup`（宿主是工程里的模块时加 `module`，例如 `setup --module app`）。它会编译安装（首次安装时点手机上的安装确认），再开启服务（系统允许时用 settings，否则在设置界面里点）。手机要输入密码、解锁时，告诉人。
3. 服务开着但没连上：通常是 uiautomator / ATX / Appium 在运行，关掉后等几秒。
4. 记下宿主注册的自定义动作 / 条件和全局拦截器（全局拦截器已经处理的弹窗，流程里不用再管）。
5. 找到宿主项目里流程放在哪、怎么写：搜 `new Flow.Builder(`、`FlowParser.parse`、`assets/flows`。**跟着项目已有的约定走**；没有约定时，在宿主模块里新建一个 `flows` 包，按功能分类写静态方法（Apex 的 runner demo 里还要在 `CodeFlows` 登记一行，列表里才看得到）。

## 第 1 步：定计划

用 `plan`（新任务加 `new: true`）写下目标和 3～6 个里程碑，每个里程碑写清**到了会看到什么**，例如：

```json
{"goal": "在某商城 App 里领取今日签到奖励", "new": true, "milestones": [
  {"title": "打开 App 首页", "evidence": "底部有「首页」「我的」标签"},
  {"title": "进入签到页", "evidence": "出现「立即签到」按钮"},
  {"title": "领取奖励", "evidence": "提示「签到成功」，按钮变成「已签到」"}]}
```

需求有歧义、而且会影响流程时（例如没说要选哪个规格）先问人；不影响的就按常理假设，交付时说明。用户的叫法和界面上的不一样时，按界面上的写，交付时说明。

## 第 2 步：探索（像人一样）

先 `launch` 目标 App（`reset: true` 回到首页），然后每一步都按这个循环：

1. **看**：`observe`（或上一步 `act` 的返回）。
2. **想**，回答四个问题：
   - 我在哪？（页面编号、标题、路径）
   - 上一步的结果符合意图吗？（预期 ✓/✗、变化、警告）
   - 离下一个里程碑更近了吗？
   - 下一步做什么最可能推进？入口不在屏幕上时，按顺序试：`find_text` 加 `scroll` 往下找 → 页面上的搜索框 → 菜单 / 「更多」 → 底部或顶部的标签页 → 返回上一层换个入口。
3. **做**：`act`，**必须带 `intent`**，尽量带 `expect`。`expect` 的键：`text`（页面上有这段文字，包含即可）、`gone`（没有这段文字）、`page`（页面编号或标题）、`package`、`changed`、`has` / `hasNot`（选择器，例如 `{"id": "notify_switch", "checked": true}`；直接把选择器当 `expect` 也行）。开关、单选的状态用 `has` 核对。
4. 看到某个里程碑的标志后，`plan` 标记 `done`。

**纠错规则**（`act` 的 ⚠ 会提醒你）：

- 页面没变化：可能点错了元素、点到了被遮挡的地方，或者还在加载。先 `observe` 加 `wait_ms` 再看，再考虑换个元素。
- 离开了目标 App（广告、应用商店）：`back`；回不去就 `launch --reset` 重来。
- 弹窗：权限、更新、广告、评分、协议……先处理掉（看清楚再决定允许还是拒绝；功能需要的权限要允许），**记下来**：它在流程里要做成拦截器。
- 在几个页面之间打转，或者很多步没有完成里程碑：停下来，`history` 看一遍路径，换一条路或重新规划。
- 同一个错误不要连续犯两次：第二次失败就换方法。

**探索时顺手收集写流程要用的东西**：

- 到过的每个页面会被自动保存为样本（`pages/P*.json`）；同一页面内容变化较大时（滚动后、开关状态变了）会另存 `P3.2`、`P3.3`……，`history` 里能看到。还想要某个状态下的样本，用 `observe --save 路径` 另存。
- 滑块看 `range`（例如 `30/0..100 可设值`），用 `setProgress`；判断「已经拉满」用选择器的 `progressAtLeast`。
- 开关、单选看 `[开]/[关]` 和 `状态=`，写流程时要考虑「已经是目标状态」的分支。
- 滚轮选择器（时间、日期、数量）的每一列常是标成不可见的虚拟节点，页面结构里会标出来，文字通常是当前值加上说明；选择器要加 `"visible": false`，用 `scrollTo` 拨到想要的值。先 `act` 拨一下看清方向（forward 是加还是减）。

## 第 3 步：写流程代码

1. `history` 回顾成功路径；对每个要用到的页面调用 `features` 拿到独有特征和推荐 matcher。推荐只是起点：它只对照了这次到过的页面，挑的时候按 [references/selectors.md](references/selectors.md) 自己判断。
2. 在宿主项目里用 **Java DSL** 写流程（[references/flow-dsl.md](references/flow-dsl.md)；语义、默认值和常用写法见 [references/flow-json.md](references/flow-json.md)，两种写法是同一个模型）。内置的条件和动作能表达的就别写代码；比较数值、按规则挑一项、需要循环时用内联的 `Match.custom(screen -> ...)` / `Actions.run(ctx -> ...)`。要点：
   - 一个页面一个状态：`match` 用页面独有的、稳定的特征（标题、固定的标签文字、语义 id），加 `pkg(...)`；动作用 `act` 结果里验证过的选择器（JSON 写法 `{"id": "x"}` 对应 `By.id("x")`）。
   - 从任何起点都能跑：起始状态通常是 `always()` + `launchApp(...)`，后面的状态再识别首页。`launchApp` 之后落在哪一页因 App 和 ROM 而异（有的回首页，有的停在上次的深层页面），**先实测**：把目标 App 停在深层页面，再 `act launch 包名` 看落在哪。
   - 目标已经达成时（开关已经开着、今天已经签过到）走一个直接成功的分支，保证流程可以重复跑。
   - 探索时遇到的弹窗做成拦截器（宿主已有全局拦截器的除外）。
   - 屏幕外的入口用 `scrollTo`，不要用固定次数的 `swipe`。
   - 「同一个列表项里同时有 A 和 B」用 `hasDescendant`，不要写成两个独立的 `has`（可能分属两行）；操作那一行里的控件用 `inside`。
   - 不确定的地方宁可多加一个状态，也不要把多页的操作塞进一个状态的动作列表里。
3. `deploy` 编译安装（几秒到几十秒，编译错误会原样返回，修了再 deploy），然后 `validate com.foo.flows.XxxFlows#method` 修到通过。
4. `check com.foo.flows.XxxFlows#method`，用 `labels` 把探索时的样本对应到状态（例如 `{"P2": "home", "P2.2": "home_scrolled"}`）。只写 `P2` 时它的附加样本 `P2.2` 等也算同一个状态；附加样本可能是完全不同的屏幕（例如同一个 Activity 的另一个标签页），先看 `history` 里每个样本的说明，不是同一状态的要单独写出来。命令行写 `check com.foo.flows.XxxFlows#method --label P2=display P5=done`；要加上自己另存的样本时，用 `--samples` 列出会话的 `pages` 目录和这些文件（这时 `--label` 的键写样本文件名）。所有警告都要处理或说清楚为什么可以忽略。

## 第 4 步：真机运行，修到通过

1. 把目标 App 放到一个普通的起点（例如 `launch --reset` 打开它，或回到桌面）。
2. `run com.foo.flows.XxxFlows#method`。不是 SUCCESS 就读轨迹：最后几条 WAIT 会说明每个候选状态为什么不匹配，失败时还有最后一屏的节点树。对照 [references/troubleshooting.md](references/troubleshooting.md) 改代码 → `deploy` → 再跑。
3. 通过以后做两次「自测」：
   - 换个起点再跑（目标 App 停在别的页面、在后台）。
   - 目标已经达成时再跑一次，应该直接成功。
4. 测试会改设备状态（系统设置、开关、新建的数据）的，**改之前先记下原值**（页面上的值，必要时用只读命令查），结束后恢复原样；恢复不了的告诉人改了什么。
5. 屏幕长时间没操作会变暗甚至熄屏，`observe` / `act` 会提示。变暗时亮度之类的读数不准，不要在这时保存样本。

一个问题修了 3 轮还没解决时，停下来把情况、轨迹和你的判断告诉人。

## 第 5 步：交付

- 交付宿主项目里的 DSL 代码（已经编译、在真机上跑通）。
- **只在项目需要 JSON 时才导出**：要远程下发、要放进 assets、宿主本来就用 JSON 加载流程、要 `push` 到 runner。用 `export com.foo.flows.XxxFlows#method -o 路径`，设备上会确认 JSON 解析回来和 DSL 完全相等；流程里有内联代码时不能导出，会说明在哪——需要的话把那段代码注册成名字（`Apex.registerMatcher` / `registerAction`）再导出。DSL 仍是唯一的源头，JSON 不要手改。
- 汇报：流程做了什么、代码在哪、每个状态对应哪个页面、做了哪些假设、哪些步骤需要人、真机运行结果（包括自测），以及导没导出 JSON、为什么。
